## 1. Functional Requirements (FR)

| Req ID | Category | Requirement | User / Stakeholder | Priority | Scope | Acceptance Criterion | Verification | Dependencies | Status |
|---|---|---|---|---|---|---|---|---|---|
| `FR-AUTH-001` | Functional / Security | The system must allow visitors to register a `PATIENT` account with a unique, normalized email address and a strong password hashed via `password_hash()`. | Patient | Must | MVP | Submitting valid registration data creates a `users` row (`role='PATIENT'`) and linked `patients` row, hashes the password, queues a verification email in `email_outbox`, and returns `201 Created`. Submitting a duplicate email returns `409 Conflict` (`EMAIL_ALREADY_EXISTS`); supplying `role='ADMIN'` or `role='DENTIST'` in the payload is ignored or rejected. | Automated API integration test | `001_create_users.sql`, `002_create_patients.sql` | Approved |
| `FR-AUTH-002` | Functional / Security | The system must authenticate users via email and password, regenerate the session ID upon login, and issue an `HttpOnly`, `SameSite` session cookie plus CSRF token. | All Roles | Must | MVP | Valid credentials return `200 OK` with user profile and permitted role; session ID changes post-login; invalid credentials or inactive accounts (`is_active=0`) return `401 Unauthorized` with a generic error message. | Automated API integration test | `FR-AUTH-001` | Approved |
| `FR-AUTH-003` | Functional / Security | The system must allow authenticated users to log out and immediately invalidate their server-side session and real-time socket authorization. | All Roles | Must | MVP | Calling `POST /api/v1/auth/logout` destroys the session; subsequent requests with the old cookie to `GET /api/v1/me` return `401 Unauthorized`. | Automated API integration test | `FR-AUTH-002` | Approved |
| `FR-AUTH-004` | Functional / Security | The system must support single-use, expiring hashed tokens in `auth_tokens` for email verification and password reset. | All Roles | Must | MVP | Using a valid verification or reset token succeeds once (`used_at` populated); reusing the same token or using an expired token (`expires_at < NOW()`) returns `422` / `400` and does not mutate account state. | PHPUnit unit & integration test | `auth_tokens` migration | Approved |
| `FR-PUB-001` | Functional / Usability | The public landing page must display clinic details, booking steps, role benefits, and live active dental services fetched from `GET /api/v1/services`, and route the "Book Appointment" CTA through login/registration when signed out while restoring the booking destination afterward. | Public Visitor / Patient | Must | MVP | Landing page renders all 8 approved sections; service cards display backend-supplied name, description, duration, and price with loading/empty/error states; clicking "Book Appointment" while unauthenticated redirects to `/login?redirect=/patient/book` (or equivalent state) and lands on the booking wizard after login. | Vitest component test & browser E2E check | `FR-SRV-001`, Landing Page Guide | Approved |
| `FR-PAT-001` | Functional | Authenticated patients must be able to view and update their own permitted profile fields (`first_name`, `last_name`, `birth_date`, `phone`, `address`) without accessing other patients' records. | Patient | Must | MVP | `GET /api/v1/me` and profile update endpoints return and modify only the authenticated user's record; attempting to read or update another `patient_id` returns `403 Forbidden`. | Automated API integration test | `FR-AUTH-002` | Approved |
| `FR-PAT-002` | Functional | Authorized admins must be able to search, paginate, view, create, and update patient profiles. | Admin / Receptionist | Must | MVP | `GET /api/v1/patients` supports pagination (`page`, `per_page <= 100`) and search query for `ADMIN` users; non-admin callers receive `403 Forbidden`. | Automated API integration test | `FR-AUTH-002` | Approved |
| `FR-DEN-001` | Functional | Authorized admins must be able to create, update, activate, and deactivate dentist profiles (`specialization`, `license_number`, contact info, `is_active`), while public/patient users can list only active dentists (`is_active=1`). | Admin, Patient | Must | MVP | Deactivating a dentist sets `is_active=0` without deleting historical `appointments`; `GET /api/v1/dentists` for public/patients excludes inactive dentists. | Automated API integration test | `003_create_dentists.sql` | Approved |
| `FR-SRV-001` | Functional | Authorized admins must be able to create, update, activate, and deactivate dental services (`name`, `description`, `price`, `duration_minutes`, `is_active`), and historical appointments must retain price and duration snapshots. | Admin, Patient | Must | MVP | Updating a service's `price` or `duration_minutes` affects new bookings only; existing rows in `appointments` retain their original `price_snapshot` and `duration_snapshot`. Inactive services cannot be selected for new bookings. | PHPUnit integration test | `004_create_services.sql`, `appointments` migration | Approved |
| `FR-SCH-001` | Functional | Authorized admins must be able to configure recurring weekly working hours (`dentist_schedules`) and blocked/time-off periods (`dentist_time_off`) for each dentist, and dentists must be able to view their own schedule. | Admin, Dentist | Must | MVP | Admin can create/update/delete schedule blocks where `start_time < end_time`; overlapping schedule definitions or invalid weekdays are rejected with `422 Unprocessable Entity`. | PHPUnit unit & integration test | `dentist_schedules` migration | Approved |
| `FR-AVL-001` | Functional | The availability endpoint (`GET /api/v1/availability`) must return only valid, bookable time slots for a given active `dentist_id`, active `service_id`, and `date`. | Patient, Admin | Must | MVP | Returned slots fit completely within the dentist's active working hours for that weekday, exclude `dentist_time_off` intervals, exclude past timestamps/advance-notice violations, and exclude intervals overlapping existing blocking appointments (`existing.start_at < slot_end AND existing.end_at > slot_start`). | PHPUnit unit & integration test | `FR-SCH-001`, `DEC-POL-001`..`004` | Approved |
| `FR-BOOK-001` | Functional / Reliability | The system must create appointment requests inside an InnoDB transaction using row-level locking (`SELECT ... FOR UPDATE` on the target dentist record) and interval-overlap validation to prevent double booking. | Patient, Admin | Must | MVP | When two concurrent `POST /api/v1/appointments` requests attempt to reserve overlapping intervals for the same dentist, exactly one commits with `201 Created` (`status='PENDING'`), and the competing request rolls back and receives `409 Conflict` (`SLOT_UNAVAILABLE`). | Automated concurrency integration test | `FR-AVL-001`, `DEC-POL-004`, `DEC-POL-013` | Approved |
| `FR-BOOK-002` | Functional | Authorized admins must be able to approve (`CONFIRMED`) or reject (`REJECTED` with safe reason) a `PENDING` appointment request via `PATCH /api/v1/appointments/{id}/decision`. | Admin / Receptionist | Must | MVP | Admin approval transitions `PENDING -> CONFIRMED`; rejection transitions `PENDING -> REJECTED` and stores the decision actor, timestamp, and reason. Patients or dentists calling this endpoint receive `403 Forbidden`. Attempting to decide a non-`PENDING` appointment returns `409 Conflict`. | Automated API integration test | `FR-BOOK-001` | Approved |
| `FR-BOOK-003` | Functional | Patients and admins must be able to cancel appointments (`PATCH /api/v1/appointments/{id}/cancel`) and reschedule appointments strictly in accordance with approved clinic state and deadline policies. | Patient, Admin | Must | MVP | Patient can cancel own `PENDING` anytime or `CONFIRMED` (`>= 24h` before `start_at`), transitioning it to `CANCELLED` and releasing the time slot on commit. Cancelling another patient's appointment returns `403`; cancelling outside policy window or from `COMPLETED`/`REJECTED` returns `409 Conflict`. | PHPUnit unit & integration test | `DEC-POL-007`, `DEC-POL-008` | Approved |
| `FR-BOOK-004` | Functional | Authorized dentists (for assigned visits) or authorized admins must be able to transition a `CONFIRMED` appointment to `COMPLETED` in accordance with clinic completion rules. | Dentist, Admin | Must | MVP | Transitioning `CONFIRMED -> COMPLETED` succeeds for the assigned dentist (or authorized admin); transitioning `PENDING -> COMPLETED` directly is rejected with `409 Conflict`. | PHPUnit unit & integration test | `DEC-POL-011` | Approved |
| `FR-TRT-001` | Functional / Privacy | Assigned dentists must be able to create and view clinical treatment records (`diagnosis`, `treatment_notes`, `recommendations`) linked to an authorized appointment (`POST /api/v1/appointments/{id}/treatment-records`). | Dentist | Must | MVP | Only the dentist assigned to the appointment may author treatment records; unassigned dentists and unauthorized users receive `403 Forbidden`. Treatment record content is never included in email bodies or Socket.IO event payloads. | Automated API integration test | `treatment_records` migration, `DEC-POL-012` | Approved |
| `FR-NOT-001` | Functional / Reliability | Every appointment lifecycle change (`requested`, `confirmed`, `rejected`, `cancelled`) must persist an in-app `notifications` row and an `email_outbox` row within the same database transaction as the appointment write. | All Roles | Must | MVP | After any booking or status transition commits, corresponding rows exist in `notifications` and `email_outbox`; users can list their own notifications (`GET /api/v1/notifications`) and mark them read (`PATCH /api/v1/notifications/{id}/read`). | PHPUnit integration test | `notifications`, `email_outbox` migrations | Approved |
| `FR-NOT-002` | Functional / Reliability | The background email worker (`ProcessEmailOutbox`) must deliver queued emails via `PHPMailer` over SMTP, mark sent jobs complete, and retry transient failures with backoff without blocking or rolling back committed appointments. | System / All Roles | Must | MVP | Simulated SMTP failure during outbox processing increments `attempts`, records a safe `last_error`, schedules `next_attempt_at`, leaves the committed `appointments` row intact, and stops retrying once max attempts or permanent recipient error is reached. | PHPUnit integration test with fake/mock mailer | `FR-NOT-001` | Approved |
| `FR-NOT-003` | Functional / Security | The `Node.js + Socket.IO` service must authenticate client handshakes via short-lived server-issued tickets, assign rooms server-side (`user:<id>`, `role:admin`, `dentist:<id>`), and broadcast minimal post-commit events published by PHP over an authenticated internal channel. | All Roles | Must | MVP | Unauthenticated or expired-ticket socket connections are rejected; client attempts to join arbitrary rooms are ignored; disconnected users recover missed notifications via `GET /api/v1/notifications` upon reconnect. | Vitest / Node `events.test.js` & API integration test | `FR-NOT-001` | Approved |
| `FR-REP-001` | Functional | The system must provide role-appropriate dashboard KPI counts and a filterable, paginated admin appointment report (`GET /api/v1/admin/reports/appointments`) derived from live MySQL queries. | Admin, Dentist, Patient | Must | MVP | Dashboard totals (today's appointments, pending requests, confirmed, completed, cancelled, active dentists) match exact database row counts for the seeded test dataset; filters by date range, dentist, service, and status return accurate paginated results. | Automated API integration test | `FR-BOOK-001` | Approved |
| `FR-AUD-001` | Functional / Security | The system must record every appointment status transition (`actor_user_id`, `old_status`, `new_status`, `reason`, `created_at`) and sensitive administrative/security events (`audit_logs`) without logging passwords, tokens, or raw clinical notes. | Admin / Security | Must | MVP | Every status transition creates a history/audit record; inspecting log outputs and audit rows confirms zero plaintext passwords, session IDs, or reset tokens are stored. | PHPUnit integration test & log inspection | `audit_logs` migration | Approved |

## 2. Non-Functional Requirements (NFR)

| Req ID | Category | Requirement | User / Stakeholder | Priority | Scope | Acceptance Criterion | Verification | Dependencies | Status |
|---|---|---|---|---|---|---|---|---|---|
| `NFR-SEC-001` | Security | All database queries must use PDO prepared statements with bound parameters, and dynamic `ORDER BY` / filter identifiers must be validated against strict server-side allowlists. | Security / All Users | Must | MVP | Static code review and SQL injection test payloads on search/filter/sort parameters return `422` or safe results without SQL syntax errors or data leakage. | Code inspection & security integration test | PHP PDO foundation | Approved |
| `NFR-SEC-002` | Security | State-changing endpoints (`POST`, `PUT`, `PATCH`, `DELETE`) authenticated via cookies must enforce CSRF token validation and strict CORS origin allowlisting, and login/registration/reset routes must enforce rate limiting. | Security / All Users | Must | MVP | State-changing request without valid CSRF header returns `403 Forbidden`; repeated rapid failed logins exceed threshold and return `429 Too Many Requests`. | Automated API security test | `FR-AUTH-002` | Approved |
| `NFR-PRI-001` | Privacy | Public endpoints, email bodies, Socket.IO payloads, Prometheus metrics, and Nginx/application logs must never expose patient diagnosis/treatment notes, passwords, tokens, or unrelated patients' PII. | Patient / Privacy Lead | Must | MVP | Inspection of email templates, socket payloads, `/metrics` output, and error responses confirms zero clinical notes, patient IDs in metric labels, or stack traces. | Automated test & security checklist inspection | `FR-TRT-001`, `NFR-OBS-001` | Approved |
| `NFR-REL-001` | Reliability | Every multi-table write (booking + status history + notification + email outbox) must execute inside a single atomic MySQL InnoDB transaction that rolls back completely if any step fails. | All Users | Must | MVP | Forcing an exception mid-transaction leaves zero orphan rows in `appointments`, `notifications`, or `email_outbox`. | PHPUnit integration test | MySQL InnoDB | Approved |
| `NFR-PRF-001` | Performance | All potentially growing list endpoints (`appointments`, `patients`, `notifications`, `reports`) must enforce server-side pagination with a bounded maximum page size (`per_page <= 100`) and composite database indexes on common filter columns. | All Users | Must | MVP | Requesting `per_page=1000` is capped or rejected with `422`; `EXPLAIN` plans on appointment lookup by `(dentist_id, start_at)`, `(patient_id, start_at)`, and `(status, start_at)` use defined indexes. | API test & MySQL `EXPLAIN` inspection | Phase 4 Migrations | Approved |
| `NFR-ACC-001` | Accessibility / Usability | The React UI must use semantic HTML, keyboard-navigable controls, visible focus states, associated form `<label>` elements, WCAG AA text contrast on brand tokens, `prefers-reduced-motion` support, and status badges that pair color with readable text/icons. | All Users | Must | MVP | All interactive controls are reachable via `Tab`/`Enter`/`Escape`; every `<input>` has an accessible label; no status is conveyed by color alone; zero horizontal overflow at `375px`, `768px`, and `1280px` widths. | Vitest component tests & manual accessibility audit | UI/UX Design Guides | Approved |
| `NFR-MNT-001` | Maintainability | The backend must separate HTTP routing/controllers, business services, PDO repositories, validators, and middleware, and every `/api/v1` endpoint must be documented in `backend/docs/openapi.yaml` and validated in CI. | Development Team / Reviewer | Must | MVP | Controllers contain zero raw SQL queries; `./vendor/bin/openapi` generates a valid OpenAPI 3.x spec in CI without errors; API responses follow `{ "data": ..., "meta": ..., "error": ... }`. | CI pipeline & code review | `swagger-php` | Approved |
| `NFR-OPS-001` | Maintainability / Portability | The full stack must start reproducibly via `docker compose` with Nginx as the sole public web entry point in production, while PHP-FPM (`9000`), MySQL (`3306`), Socket.IO internal publishing, Prometheus, and exporters remain on private Docker networks. | DevOps / Reviewer | Must | MVP | `docker compose config` and `nginx -t` pass; inspecting published ports in `docker-compose.prod.yml` confirms only Nginx `80`/`443` are exposed publicly; `/health` and `/api/v1/health` respond `200 OK`. | CI check & container smoke test | Docker Compose v2 | Approved |
| `NFR-OBS-001` | Observability | Prometheus must scrape configured internal targets and exporters with low-cardinality labels, and Grafana must load version-controlled datasources, dashboards, and alert rules automatically on container startup. | Operations / Admin | Must | MVP | Prometheus targets report `UP`; Grafana loads `toothcare-overview.json` via provisioning files; stopping a monitored service triggers the `TargetDown` alert condition. | Container verification drill | Phase 19 Monitoring | Approved |
