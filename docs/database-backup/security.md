# ToothCare Hub — Database Backup Security & Cryptography

**System:** ToothCare Hub — Dental Appointment and Clinic Management System  
**Document:** Backup Security & Cryptography Specification  
**Version:** 1.0.0-Production  

---

## 1. Threat Model & Compliance

Dental clinic databases contain protected health information (PHI), personally identifiable information (PII), patient medical histories, dental radiographs/notes, and hashed user credentials.

### Threat Vectors Addressed:
1. **Physical or Cloud Storage Theft**: If backup archives are intercepted or exfiltrated from disk/cloud storage, strong encryption renders them completely unreadable without the private key.
2. **Archive Tampering & Bit-Flipping**: Attackers modifying SQL commands or injection attacks inside backups are blocked by authenticated GCM tag verification.
3. **Process-Level Credential Snooping**: Attackers running `ps aux` or inspecting `/proc` cannot read database passwords because credentials are never passed as command-line arguments.
4. **Accidental Repository Commits**: Backup files and encryption keys are strictly excluded by Git ignore patterns.

---

## 2. Authenticated Encryption Layer (AES-256-GCM)

ToothCare Hub utilizes **AES-256-GCM** (Galois/Counter Mode), an authenticated symmetric cipher providing both **confidentiality** and **authenticity**.

### 2.1 Binary Archive Layout

Every `.sql.gz.enc` file is structured as follows:

```
+-------------------+-----------------------------+------------------------------------+
| IV (Nonce)        | GCM Authentication Tag      | Ciphertext (Compressed SQL Dump)   |
| 12 Bytes          | 16 Bytes                    | Variable Length                    |
+-------------------+-----------------------------+------------------------------------+
```

- **Initialization Vector (IV)**: 12 bytes generated per backup using `random_bytes(12)`. An IV is never reused.
- **Authentication Tag**: 16 bytes generated by `openssl_encrypt($data, 'aes-256-gcm', $key, OPENSSL_RAW_DATA, $iv, $tag)`.
- **Ciphertext**: AES-256 encrypted GZIP stream.

### 2.2 Tamper Detection Guarantee

During restoration or integrity verification, `openssl_decrypt()` verifies the 16-byte authentication tag against the ciphertext and IV. If even a single byte of ciphertext or IV is altered, decryption fails immediately with `false`, and restoration aborts before any SQL is executed.

## 3. Process Credential Protection

### The Vulnerability:
Running `mysqldump -u user -psecret database` exposes the plaintext database password to any unprivileged user executing `ps -ef` or inspecting `/proc/$PID/cmdline`.

### The Solution:
`DatabaseBackupService` writes database credentials to a temporary MySQL option file with restricted permissions (`0600`):

```ini
[client]
host="127.0.0.1"
port="3306"
user="toothcare_user"
password="[REDACTED]"
```

The dump command is invoked using:
```bash
mysqldump --defaults-extra-file=/tmp/tc_cnf_xxxxxx.cnf toothcare_hub ...
```

In a PHP `finally` block, the temporary credentials file is securely unlinked immediately after `mysqldump` terminates, ensuring no credentials remain on disk.

## 4. Repository & Filesystem Permissions

### 4.1 Git Exclusions (`.gitignore`)
The root `.gitignore` enforces exclusion of all backup artifacts and key material:

```gitignore
# Database Backups & Cryptographic Keys
/backups/
*.sql
*.sql.gz
*.sql.gz.enc
*.sha256
*.backup-meta.json
*.key
*.pem
```

### 4.2 Linux File Access Restrictions
On staging and production servers, ensure strict POSIX ownership and permissions:

```bash
# Secure the environment configuration
chown www-data:www-data .env backend/.env
chmod 0600 .env backend/.env

# Secure the backup storage directory
chown -R www-data:www-data backups/
chmod 0700 backups/
chmod -R 0600 backups/*/*.enc
chmod -R 0600 backups/*/*.json
chmod -R 0600 backups/*/*.sha256
```

## 5. Encryption Key Lifecycle & Rotation

### 5.1 Storage Guidelines
- **Primary Runtime**: Loaded via `BACKUP_ENCRYPTION_KEY` from system environment or `.env`.
- **Off-Site Escrow**: Maintained in an encrypted organization vault (1Password / HashiCorp Vault / AWS KMS).
- **Separation of Concerns**: Never store the encryption key on the same cloud bucket or server hosting the `.sql.gz.enc` files.

### 5.2 Key Rotation Procedure
To rotate the backup encryption key:
1. Generate a new 32-byte key: `openssl rand -hex 32`.
2. Decrypt existing historical backups using the old key and re-encrypt with the new key, or preserve the old key in your password vault for historical backups and apply the new key to all subsequent backups.
3. Update `BACKUP_ENCRYPTION_KEY` in production environment settings.
4. Execute a manual backup (`php database/scripts/backup.php`) and isolated test restore to verify the new key.
